# Site-code conflict discards a real secondary site (one scalar site_code per target)

TargetEntry.site_code is a single scalar and context.py:430-438 resolves conflicts as 'first writer wins; warn on conflict'. A host can legitimately belong to two sites at once: mayyhem.com's ps1-sec.mayyhem.com is a CLIENT DEVICE of the PS1 primary site AND the host where the real SEC secondary site's site system roles are installed (confirmed by @_Mayyhem 2026-07-31). ps1-sec registers with site_code PS1 first, so the later SEC discovery is discarded with a WARNING and the SEC secondary site never reaches the graph. Observed 4x in a lowpriv full-domain run: "Target 'ps1-sec.mayyhem.com' already has site_code 'PS1'; ignoring 'SEC'". Consequence: node-site-count and node-site-has-sitecode fixtures fail (expect 3 sites CAS+PS1+SEC, graph has 2), and this plausibly explains downstream count mismatches (SCCM_AssignAllPermissions found 6). NOTE: do NOT update the fixtures to match -- the fixtures are correct and the collector is wrong. Likely needs site_code to become a collection, or to distinguish 'client of site X' from 'hosts site systems for site Y'.

## Acceptance Criteria

A host that is a client of one site and a site system of another carries both site codes; the SEC secondary site appears in the graph; node-site-count and node-site-has-sitecode pass against the mayyhem lab; no site-code discovery is silently discarded.

## Notes

**2026-07-31T15:41:47Z**

CORRECTION to the description's framing (@_Mayyhem 2026-07-31): ps1-sec is NOT a member of two sites. It is a client device of PS1 only. It merely HOSTS the SEC secondary site's site system roles. So the defect is not 'a host can belong to two sites' -- it is that TargetEntry.site_code conflates two different relations into one scalar:
  (1) CLIENT MEMBERSHIP -- which site this host is a client of (ps1-sec -> PS1)
  (2) SITE-SYSTEM HOSTING -- which site's roles this host runs (ps1-sec -> SEC)
'First writer wins' then drops whichever relation is discovered second. Fix direction is therefore NOT 'make site_code a set' (that would wrongly model ps1-sec as a member of both PS1 and SEC); it is to represent hosting separately from membership, so the SEC secondary site can be discovered from its host without claiming that host as a SEC client.
Fixture consequence (decision confirmed with @_Mayyhem): assertions go to HOST LEVEL, since the lab hostnames are stable. The fixtures should pin: 3 sites exist (CAS + PS1 + SEC); ps1-sec is a PS1 client device; ps1-sec hosts the SEC site systems. Count-only assertions are what let this bug hide.

**2026-07-31T15:56:40Z**

SCOPE REFINEMENT from the privileged/unprivileged A/B (2026-07-31): node-site-count and node-site-has-sitecode land in the needs_privilege bucket -- they PASS with SCCM-admin privilege and FAIL only at low privilege. So this data loss is LOW-PRIVILEGE-ONLY: with AdminService/WMI reachable, the SEC site is reported directly by the provider and the site survives by another route. At low privilege the only source for SEC is HTTP/role discovery on ps1-sec, and that is exactly the discovery 'first writer wins' throws away.
Repro requires lowpriv creds: uv run openhound collect sccm ./out/unpriv -u 'MAYYHEM\lowpriv' -p '<pw>' --run-integration-tests --clean -> 2 sites instead of 3.
This makes it a low-privilege attack-surface gap specifically: an operator with only a domain user never sees the SEC secondary site, which is precisely the tier where the collector's value is highest.

**2026-07-31T16:21:10Z**

MECHANISM NAILED DOWN (answering 'isn't SEC created during LDAP collection?' -- no):
- LDAP finds only 2 mSSMSSite objects in BOTH privileged and unprivileged runs. SEC is not published to AD, so the LDAP phase never creates it. Filter used: (objectClass=mSSMSSite) under CN=System Management.
- The discard warning fires 4x in BOTH runs, so the scalar site_code conflict is privilege-independent. Two of the four are for ps1-mp, two for ps1-sec, both from the HTTP phase.
- Resulting graphs: priv = ['PS1','SEC','CAS'] (3), unpriv = ['PS1','CAS'] (2).
So privilege does not change the discard -- it supplies an ALTERNATIVE source. AdminService/WMI reports the site hierarchy including the SEC secondary, creating the SCCM_Site node independent of any target's site_code. Without privilege the only SEC evidence is (a) the HTTP probe on ps1-sec and (b) SMB share enumeration ('SMS_SEC (SMS Site SEC 12/01/25)', 'SCCMContentLib$ ... for site SEC'), and both feed the target's scalar site_code, which first-writer-wins discards.
Consequence for the fix: it is not enough to stop discarding -- a site discovered only as 'this host serves site X' must still be able to create the SCCM_Site node without claiming the host as a member of X.

**2026-07-31T18:36:55Z**

ROOT CAUSE CORRECTED (2026-07-31) -- my earlier diagnosis was wrong. The register_target scalar site_code discard is real, but it is NOT what loses SEC. Followed the data through a lowpriv full-lab run:
  smb_sites.site_code       = ['CAS','PS1','SEC']   <- SEC collected
  remoteregistry_sites      = ['CAS','PS1','SEC']   <- SEC collected
  site_hierarchy.site_code  = ['CAS','PS1','SEC']   <- SEC survives preprocess
  node_site.site_code       = ['CAS','PS1']         <- SEC dropped HERE
SEC reaches preprocess by other paths regardless of the register_target discard. The loss is in _node_site (transforms.py:1838), whose docstring lists its only sources as adminservice_sites/wmi_sites, adminservice_site_definitions/wmi_site_definitions, ldap_sites, and adminservice_site_systems/wmi_site_systems. It never reads smb_sites, remoteregistry_sites or http_site_servers. site_hierarchy was widened to every site-code source (see README 'Collection privilege tiers'); node_site was not. The existing LEFT JOIN to site_hierarchy only STAMPS root_site_code/sql_service_account_name onto rows that already exist -- it cannot add one.
Privileged passes only because AdminService/WMI supply SEC as a source row. Comparison:
  unpriv3 site_hierarchy SEC = parent None, type None, root CAS  -> node_site CAS, PS1
  priv3   site_hierarchy SEC = parent PS1,  type 1,    root CAS  -> node_site CAS, PS1, SEC
FIX DIRECTION: _node_site should emit a row for any site_code present in site_hierarchy that no other source supplied. The low-priv row will be sparser (no parent/type), which the assumed-vs-confirmed model already handles. This also means the membership-vs-hosting modelling question is a SEPARATE concern from the missing node -- it does not block this fix.
