# Wire collected-but-unread site-code and role sources into preprocess (site_hierarchy D5 + node_computer orphaned roles)

Completeness audit (2026-07-27) found raw tables that are collected, registered in `_preproc_table_map`, loaded into the DuckDB lookup, and then read by NO transform. Folded into `sccm/sccm/docs/superpowers/plans/2026-07-23-low-priv-assumed-edges.md` (Task 1 amended, new Task 1b) and the design spec (new §2.1 / §4.1, decisions D5 / D6).

## Scope A -- `site_hierarchy` is starved (D5)

`_site_hierarchy` INSERTs only from `adminservice_site_definitions` + `wmi_site_definitions`. Fourteen other raw tables carry a `site_code` and none reaches it: `ldap_management_points_raw`, `ldap_sites`, `remoteregistry_sites`, `smb_sites`, `smb_computers`, `http_management_points` / `_distribution_points` / `_smsproviders` / `_site_servers`, `http_site_versions`, `dns_management_points`, `local_wmi_sms_authority` / `_lookupmp` / `_ccm_client`, `ldap_cmrc_devices`.

An empty `site_hierarchy` means `_root_code` returns None and every `nonsec`-gated edge family emits zero rows. Note `ldap_sites` IS already read by `_node_site`, so a low-priv run can emit `SCCM_Site` nodes while the hierarchy table that gates every edge stays empty.

Fix: a bespoke arm for the hierarchy-shaped MP-capabilities source (it carries type/parent/root), plus an `information_schema`-discovered loop for the bare-code tables so the list cannot go stale.

## Scope B -- three orphaned role sources (spec §4.1)

All confirmed evidence -> emitted in both flag modes, no `assumed` stamp.

1. **`http_site_servers`** -- the ANONYMOUS sitesigncert probe (`http.py:216-254`) identifies the Site Server from the MP's site-signing cert. The only credential-free Site Server signal that exists. `SCCM_LocalAdminRequired` / `SCCM_CoerceAndRelayToAdminService` / `SCCM_CoerceAndRelayToSMB` all pivot on that role.
2. **`ldap_management_points_raw.fsp_hostname`** -- Fallback Status Point role never built. Nothing else fingerprints an FSP, and because the edge builders match a generic `role LIKE '%@%'`, an untagged host is silently dropped from two edge families.
3. **`dns_management_points`** -- the site code is authoritative (it is the SRV query key) but the collector passes it to `register_target(...)` and yields `target.ad_object` alone, so the row reaches DuckDB with no site code and no role. Needs a small collector change, unlike the other two.

## Scope C -- the MSSQLSvc SPN is collected and thrown away (spec §4.2, plan Task 1c)

Same class of bug, found 2026-07-27 while pinning down D2. An `MSSQLSvc` SPN is AD-readable proof a host runs SQL Server, and per D2(a) such a host must reach the graph as `MSSQL_Server` + `Computer` + `MSSQL_HostFor` / `MSSQL_ExecuteOnHost` in **both** flag modes. Three things stop that:

1. **The SPN is never persisted.** `collect_mssql` fetches `ctx.ad.get_spns(target)` (`mssql.py:41`) only to parse a port out of `MSSQLSvc/host:port`, then discards it. No raw table records "this host has an MSSQLSvc SPN".
2. **A filtered port erases the host.** `if not _check_port(target, port): return` (`mssql.py:63-65`) makes `mssql_server_instances` a *1433-is-reachable* table, not an *has-an-SPN* table. This contradicts D2's stated advantage of working "even when 1433 is filtered", and makes the obvious SPN predicate (`sid IN (SELECT host_sid FROM mssql_server_instances)`) silently test reachability instead. Fix: emit the row whenever the SPN exists, with EPA fields NULL when the port is closed, plus `has_mssql_spn` / `port_open` booleans. EPA-gated edges must then require the EPA columns, not the row's presence.
3. **No Computer node for an SPN-only SQL host.** `mssql_server_instances` feeds only `_node_mssql_server` (`transforms.py:2380`), never `_node_computer`, while `_edge_mssql_structural` emits `HostFor`/`ExecuteOnHost` straight off `node_mssql_server.host_sid` with no existence check (`transforms.py:3077-3083`) -- unlike `_edge_mssql_service_account`, which documents an explicit resolve-or-drop guard (`transforms.py:3131`). A SQL host not independently discovered as an SCCM system therefore gets edges pointing at a node id nothing emits.

## D6 -- site-code attribution never guesses

A host may only be tagged `<Role>@<site>` from a source that knows THAT host's site; no backfilling from "the only site in the hierarchy". One sanctioned exception: sitesigncert is an MP endpoint, so the cert issuer is that MP's site server -- stamp `mp_host` on the row (mirroring `http_site_versions`) and join in the transform, keeping the inference visible in the data. Do NOT reorder the probes (sitesigncert is ps1:8611, first).

## Flag semantics settled alongside this work (2026-07-27)

- **A confirmed site database keeps its full MSSQL scaffolding in both flag modes.** Once RR/AdminService/WMI confirms the host IS the site DB, the schema SCCM requires and defaults to there (`CM_<site>`, sysadmin, db_owner, site-server/provider machine-account logins) is a consequence of that fact, not a "possible" edge. Only `SPN+SCCM`-basis scaffolding is assumed, and it is filtered once in `_assumed_site_dbs` -- downstream builders read `basis` only to choose the provenance stamp, never to re-decide emission. Confirmed rows get `SCCM-SiteDBDefaultSchema` in `collectionSource` so the derivation stays auditable without implying doubt.
- **`HasSession` is never possible-gated**, in any arm. `_edge_has_session` (`transforms.py:2798`) already takes no flag and is called unconditionally (`transforms.py:3593`); the plan must not regress that, including Task 13's new SPN-holder arm.
- **The untyped-root fallback is gated only in the ambiguous case (D4).** With >1 untyped site, picking a root is an assumption, so `--disable-possible-edges` leaves `root_site_code` NULL. With exactly one site it is deduction and resolves in both modes. Gated carefully because the root is baked into SCCM-native node IDs (`suffix = " || '@<root>'" if root else ""`, `transforms.py:1583`, at 8 of 13 `_root_code` call sites) -- a missing root does not suppress those builders, it re-IDs their nodes, so the two modes would otherwise produce non-mergeable graphs. Logging splits the same way: WARNING when ambiguous, INFO when single-site.
