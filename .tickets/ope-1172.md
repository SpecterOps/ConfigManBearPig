## Review notes for the next change (2026-11-10)

The remaining first-answer choices are in `collectors/mssql.py:collect_mssql`,
`clients/ad.py:find_mssql_spn_holder`, and
`collectors/registry.py:get_mssql_settings` / `_read_mssql_service_state`.
`transforms.py:_node_mssql_server` already groups by host SID and port, but its
missing-port fallback to 1433 must not attach an unresolved named instance's
settings to the default instance.

Recommended approach: retain each instance's own registry path, ports, service
identity, and protection values; retain all host-matching SPN holders and associate
each account only with its advertised endpoint. Probe each known numeric port
independently. An unresolved instance name is raw evidence, not proof it listens
on 1433. Keep the existing host-SID/port graph IDs for known ports; review any
proposed change to graph identity or schema before implementing it. No SQL Browser
discovery or schema change has been implemented by the foundation work.

Microsoft's [SPN format documentation](https://learn.microsoft.com/en-us/sql/database-engine/configure-windows/register-a-service-principal-name-for-kerberos-connections?view=sql-server-ver17)
uses `MSSQLSvc/<FQDN>:<port>` for TCP and
`MSSQLSvc/<FQDN>:<instancename>` for named non-TCP connections. Do not assume every
colon suffix is numeric. Its [port configuration guidance](https://learn.microsoft.com/en-us/troubleshoot/sql/database-engine/connect/static-or-dynamic-port-config)
also requires checking Listen All versus individual IP settings and static versus
dynamic ports. A dynamic value of zero is not a listening port. Missing registry
protection values must remain unknown rather than becoming No/Off.
